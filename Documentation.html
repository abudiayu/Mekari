Wollo-Info Hub

System documentation: what we are building, who can do what, and how the parts fit together. Frontend: React + Vite (JSX). Backend: Supabase (Auth, Postgres with RLS, Storage, pgvector) plus an Express API on Render. An AI chatbot reads the site's own data to help students.

Goal

Give students trustworthy information about Wollo University and make university life easier: departments, courses, graduates, opportunities, student unions and clubs, motivation and study documents. Detailed information is shown only after login. An AI chatbot, connected to the same data as the site, tells students what they can do and how to do it, step by step, in Amharic or English.

  • Students sign in to read detailed department information, follow unions and keep a personal library.
  • Department heads manage the information of their own department.
  • Union and club accounts post news and opportunities on their own page.
  • Admin controls everything.

Account types

There are four kinds of account. Staff and heads are stored in staff_profiles with a role of admin, head, staff or union. Students are stored in students. Every account also has a row in public.users, linked to Supabase Auth.

System architecture

UsersVisitor, student, department head, union account, admin
React + Vite frontend (Vercel)Public pages, login gate, student dashboard, head page, union dashboard, admin console, chat window. Languages: en, am, om.
Express API (Render) and chat service (edge function)The API handles admin actions and protected writes. The chat service searches the data and calls the AI model.
Supabase projectAuth (email, Google) · Postgres with RLS and RPC functions · Storage (files, photos) · pgvector (chat knowledge)
AI model (external API)Answers only from the content the chat service gives it. The API key lives on the server, never in the frontend.

How a request moves

  • Login and Google sign-in go from the frontend straight to Supabase Auth.
  • Public reads and student reads go to Supabase with the user's token, so RLS decides what comes back.
  • Admin actions (create a head, remove a union account) go through the Express API, which checks the role first.
  • Chat questions go to the chat service with the user's token, so the chatbot can only read what that user may read.

Student journey

Open site→Browse public pages→Click detail→Login or register→Student dashboard
  1. A visitor sees the public pages. Clicking anything detailed redirects to /auth and returns to the same page after login.
  2. At registration the student says whether they are fresh (not yet in a department) or already in a department.
  3. A current student gets their department's detailed page. A fresh student can mark one or more departments as "interested", which department heads can see.
  4. The dashboard offers an optional personal library. A student can skip it and create it later.
  5. The chat window is available on every logged-in page for questions such as "how do I fix my registration?".

Student dashboard and library

Dashboard

  • My department: duration, courses, prerequisites, graduates, opportunities.
  • Interested departments (for fresh students).
  • Latest opportunities, motivation posts and union news.
  • Chat window.

Personal library

  • Created on demand with "Create my library". Fresh students can leave it out.
  • Only the owner can see it. RLS enforces owner_id = auth.uid() on every row.
  • A student can save official documents and upload their own files to Supabase Storage.
  • Allowed file types and size limits follow the existing media rules (blocked extensions, 20 MB per file).

Admin panel

  • Users: list of students, staff, heads, union accounts and admins with name, id, email, role and department or union.
  • Department heads: add, assign a department, change, deactivate or remove.
  • Union accounts: add a union, create its account, deactivate or remove.
  • Departments and programs: add, edit and delete dynamically under faculties such as Social Science and Informatics. The nav bar dropdowns and the Departments page read from the database.
  • Opportunities and motivation: add, edit, publish, and create a page for each opportunity.
  • Password reset: through Supabase Auth admin functions, never by showing a password.
  • Chatbot: see unanswered questions and turn them into guides.
Passwords are not viewableSupabase Auth stores passwords as hashes. They cannot be read back, and showing them would be unsafe even for an admin. The admin sees names and emails and can send a reset instead.

AI chatbot

The chatbot is connected to the site's own data. It tells students what they can do and how, using content published by the admin, department heads and unions. It answers in the language the student writes in (አማርኛ or English).

How it works

  1. Knowledge. Departments, courses, prerequisites, opportunities, motivation, union posts, documents and help guides are split into chunks and stored in knowledge_chunks with an embedding. Use a multilingual embedding model so Amharic works.
  2. Search. The chat service embeds the question and finds the closest chunks with pgvector. For personal questions it also calls database functions (for example "opportunities for my department").
  3. Answer. The AI model receives the question and the found content, and answers only from that content, with the source named.
  4. No match. The chatbot says it does not know, offers the guide categories, and logs the question in unanswered_questions so staff can write a guide.
  5. Freshness. A trigger or function re-embeds a chunk whenever its source row is created or edited.

Rules

  • The chat service uses the student's own token, so RLS limits what it can find. It never returns other students' data.
  • The AI API key stays on the server (edge function or Render). It is never in the frontend.
  • Rate limit per user. Stay on university topics. Never invent office numbers, deadlines or fees.
  • Show the source with each answer, for example "from the Computer Science department page".

Security rules

  • Check the role on the server or in RLS for every protected action. Hiding a button in React is not security.
  • Heads and union accounts can only change rows where department_id or union_id matches their own.
  • The Supabase service role key lives only in the backend environment. Never put it in the frontend or in Git.
  • The frontend uses only the public (anon) key and the user's own token.
  • Never return password hashes or secrets. Reset instead of reveal.
  • Students see only their own library and profile. Student personal data is visible only to the admin and the matching department head.
  • Keep every .env out of Git and check it was never committed.
  • Rate limit login and the chat function. Validate file types and sizes on upload.
  • Keep CORS limited to your Vercel and local origins.

Build roadmap

Small phases, each one working before the next starts.

  1. Roles and departments: add the union role, the unions table, helper functions and RLS; admin adds and removes heads and union accounts; admin adds and deletes departments dynamically.
  2. Login gate: redirect to login for detail pages and return after login; student registration with department or "fresh"; fix the registration 404 in Auth.jsx.
  3. Department head page: profile, courses, requirements, graduates, interested students, opportunities and motivation.
  4. Union pages: public union pages and the union dashboard for posting.
  5. Content on the public site: make new motivation and opportunities show on the public pages (Supabase version of the fix).
  6. Documents and student library.
  7. AI chatbot: pgvector, embedding on publish, chat function, guides with steps and photos, unanswered-question log.
  8. Admin polish and security review: RLS tests, rate limits, deployment checks.

Open decisions

  • Should union posts show publicly right away, or wait for admin approval?
  • Can a student follow several unions? Can one union have several accounts?
  • Does a student belong to one department, or can they be interested in several?
  • Should students register freely, or with a university ID number that we verify?
  • Which AI model and embedding model will the chatbot use, and what monthly budget is acceptable?
  • Which office names and numbers should the first guides cover (registration, dormitory, library, department change)?

Working notes

Notes to keep the project consistent when building with an assistant or with Kiro.

  • The backend is Supabase, not MySQL. Any fix that mentions MAMP or the old MySQL database is out of date and must be redone for Supabase.
  • Frontend files are JSX (React + Vite). When asked for code, give complete files (full JSX and CSS), not snippets.
  • When a message asks for "the prompt", deliver only the prompt text for the build tool, not the generated code.
  • Keep department-scoped and union-scoped permissions in RLS first, then mirror them in the UI.
  • Current known issues: student registration returns a 404 from Auth.jsx; new motivations do not appear on the public Motivation page; the Render backend root returns Route GET / not found.
